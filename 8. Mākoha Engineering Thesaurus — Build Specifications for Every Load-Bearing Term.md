# Mākoha Engineering Thesaurus — Build Specifications for Every Load-Bearing Term

Sep 25, 2026 · @Ken Lee

## 0. How to read this thesaurus

The canonical documents name things. This document says what each named thing is made of, so an engineer who has never seen the canon can build it: interface, data shape, algorithm, dependencies, and the test that proves it exists. Every entry follows one form.

```
TERM
  Canon:      where the term is defined (link)
  Is:         one sentence, no metaphor
  Interface:  the function, endpoint, type or table other components call
  Data:       the fields and their types
  Algorithm:  the steps, in order, deterministic where the canon requires it
  Depends on: other TERMS (by name) and external artefacts (by link)
  Test:       the acceptance test that must pass before the term is considered built
```

**Conventions.** Types are written in Rust for the core and JSON Schema for the wire; SQL is PostgreSQL. `Pin` means `{id: string, version: string, sha256: hex64}`. `Sha256` means a 32-byte digest over RFC 8785 canonical JSON. `EffectiveTime` is an RFC 3339 instant supplied by the caller, never read from a clock. A test named in an entry is the name of a CI job; it fails the merge when red. Where the canon leaves a choice, the entry says **\[decision\]** and the consolidated spec's §13 holds the owner.

## 1. Record and data plane

### RECORD

- Canon: [Spine, "The record"](https://claude.ai/code/artifact/6f3c7059-f6df-49f8-a6ba-9cbe01badb9d).
- Is: the set of all FHIR R4 resources about one patient, every version retained, every version carrying provenance.
- Interface: FHIR R4 REST (`GET/POST /fhir/{Resource}`, `_history`, `$everything`), plus the ledger read API for arguments (§7).
- Data: FHIR R4 resources with the AU Base profile; each stored row `(resource_type, id, version_id, body jsonb, last_updated, provenance_ref, consent_scope[])`; `body` is canonical JSON; `version_id` is a monotonic integer per `(resource_type, id)`.
- Algorithm: a write creates a new `version_id`; the previous version is never mutated; `DELETE` writes a tombstone version with `deleted=true` and reason; every write emits a RECORD EVENT.
- Depends on: PROVENANCE, EVENT STREAM, CONSENT, terminology snapshot (§4).
- Test: `record.versioning` writes three versions, reads each by `_history`, asserts byte equality and that `UPDATE` on the versions table is denied to every role.

### RESOURCE VERSION

- Canon: Spine, "The record" ("a correction is a new version with the reason recorded").
- Is: one immutable snapshot of a resource.
- Data: `version_id int`, `reason text NOT NULL`, `author_ref text NOT NULL`, `content_hash bytea`, `prev_version_hash bytea`.
- Algorithm: `content_hash = sha256(canonical(body))`; `prev_version_hash` = previous version's `content_hash` or NULL; trigger rejects an insert whose `prev_version_hash` mismatches.
- Test: `record.chain` tampers with a stored body and asserts the chain verification job reports the version.

### PROVENANCE

- Canon: Spine, "Provenance on every entry"; consolidated spec §7.3.
- Is: the who/when/how/from-what/under-which-consent of every record entry, stored as a FHIR `Provenance` resource per version.
- Data: `target` (the version), `recorded` (EffectiveTime), `agent[]{who: Practitioner|Patient|Device, type: author|verifier|generator|extractor, onBehalfOf}`, `entity[]{role: source|derivation|revision|quotation|instantiates, what}`, `activity` code, `signature[]` (JWS over canonical JSON), extension `capture_context: clinician-entered|patient-reported|extracted|device|imported`, extension `consent_ref`.
- Algorithm: the write path constructs Provenance in the same transaction as the version; a version without a Provenance row cannot commit (FK NOT NULL, deferred to end of transaction).
- Depends on: RESOURCE VERSION, CONSENT, SIGNATURE (§7).
- Test: `record.provenance_required` attempts a version insert without Provenance and asserts rejection.

### MASTER PATIENT IDENTITY

- Canon: Spine, "Identity".
- Is: one durable patient id with linked identifiers and a probabilistic matcher for inbound data.
- Interface: `POST /identity/match {demographics, identifiers[]} -> {candidates[]: {patient_id, score, breakdown[]}, decision: match|review|new}`; `POST /identity/merge`, `/unmerge` (both write events, never rewrite history).
- Data: `patient(patient_id ULID)`, `patient_identifier(patient_id, system, value, period, verified bool)`, `patient_link(from, to, kind: merged_into|replaced_by, act_ref)`.
- Algorithm: FELLEGI–SUNTER RESOLVER (§4) over fields {family name, given name, DOB, sex, IHI/Medicare/DVA where present, address, phone}; two ratified thresholds (upper: auto-match, lower: review); scores between go to a human review queue; identifiers with `verified=true` short-circuit to match.
- Depends on: FELLEGI–SUNTER RESOLVER, REVIEW QUEUE (§8).
- Test: `identity.threshold` seeds 1,000 synthetic pairs with known truth; precision at the upper threshold ≥ 0.999; every score in the review band produces a queue item.

### ENCOUNTER and EPISODE

- Canon: Spine, "Encounters and episodes".
- Is: Encounter = one contact of any modality (including an agent conversation); Episode = `EpisodeOfCare` grouping encounters.
- Data: FHIR `Encounter{class: AMB|VR|HH|..., type, participant[], reasonCode, period, episodeOfCare[]}`; extension `modality: in-person|video|phone|message|home-visit|agent`.
- Algorithm: every inbound item and every act (§8) is attached to an Encounter; an agent conversation creates an Encounter with `class = VR, modality = agent` at first message.
- Test: `record.encounter_for_agent` asserts an agent pre-intake creates exactly one Encounter and all QuestionnaireResponses reference it.

### PROBLEM LIST

- Canon: Spine, "Problems and conditions"; moonshot, "Clinical entity recognition".
- Is: coded `Condition` resources with status, certainty and evidence links.
- Data: `Condition{code (SNOMED CT-AU), clinicalStatus, verificationStatus, onset, bodySite, severity, evidence[]{detail: DocumentReference|Observation|DiagnosticReport}, encounter}`; extension `assertion: present|absent|possible|hypothetical|historical|family`; extension `source_span_ref` (SPAN LINK).
- Algorithm: a Condition produced by extraction is written with `verificationStatus = provisional`, `capture_context = extracted`; a clinician's confirmation (act) writes a new version with `confirmed`; problems from narrative never overwrite a clinician-entered problem, they sit beside it and are reconciled in the pre-visit brief.
- Test: `record.problem_reconcile` feeds an extracted and a typed Condition for the same concept and asserts both versions exist and the brief shows one line with two sources.

### OBSERVATION STORE

- Canon: Spine, "The store of measurements".
- Is: every measurement as FHIR `Observation` regardless of source, with reference range and method.
- Data: `Observation{code (LOINC or SNOMED), value[x] with UCUM unit, referenceRange[] (per lab, age, sex, pregnancy), method, performer, device, effective, basedOn (ServiceRequest line), derivedFrom[], hasMember[] (panels)}`; time-series store for device streams: `(patient_id, device_id, code, ts, value, quality)` in a columnar/TS table; promotion rule set writes discrete Observations.
- Algorithm: `promote(stream, rule) -> Observation` where rule is a template-declared window predicate (e.g. HR > 120 for ≥ 10 min) evaluated in fixed-point; derived values (eGFR CKD-EPI, BMI, BSA) are Observations with `derivedFrom[]` and extension `calculator_pin`.
- Depends on: terminology snapshot for LOINC axes (scale decides value slot), ORDER OBJECT for `basedOn`.
- Test: `obs.trend_across_sources` writes a BP from a clinic cuff, a home device and a patient entry; a trend query returns three points with method labels and no merge.

### MEDICATION LIFECYCLE

- Canon: Spine, "The store of treatments and prescriptions".
- Is: five linked records per medication: intent (`MedicationRequest` intent=plan), order (`MedicationRequest` intent=order), dispense (`MedicationDispense`), administration/adherence (`MedicationAdministration` / `MedicationStatement` with `capture_context`), change/cease (new MedicationRequest version with `statusReason`).
- Data: AMT code at TPUU/MPUU level; `dosageInstruction` structured; extension `reconciliation_group_id` linking the five; reconciled list = view `current_medications(patient_id)`.
- Algorithm: `reconcile(patient_id)` groups by `(ingredient set, route)` via Graph-Ontology `transcode`, marks discrepancy where practice order, external order, dispense and patient report disagree on product, dose or status; emits `DetectedIssue{code: med-discrepancy}` per group.
- Depends on: TERMINOLOGY SNAPSHOT, FELLEGI–SUNTER RESOLVER (brand→AMT), INBOUND PIPELINE.
- Test: `med.reconcile_discrepancy` (discharge letter dose ≠ patient-reported dose) yields one DetectedIssue with both sources referenced.

### ORDER OBJECT

- Canon: Spine, "Outbound: orders sent straight to the patient" and the state diagram there.
- Is: one lifecycle type for prescriptions, pathology, imaging and referrals.
- Interface: `POST /order {kind, patient, lines[], urgency, clinical_details} -> order_id`; `POST /order/{id}/sign {signer, signature}`; transitions via events.
- Data: FHIR `ServiceRequest` (pathology, imaging, referral) or `MedicationRequest` (prescription) plus a state machine row `order_state(order_id, state, entered_at, actor, reason)` with states exactly `drafted, checked, signed, transmitted, acknowledged, fulfilled, resulted, reconciled, overdue`; `expected_result_by` timestamp.
- Algorithm: `checked` requires the PRESCRIBING CHECK argument (an ActualArgument) released or the clinician's recorded override act; `signed` requires a `sign_off` act and JWS; `transmitted` fans out to provider channel, patient channel and national exchange in parallel with per-channel receipts; a timer moves `transmitted → overdue` at `expected_result_by` and writes a Task; inbound matching moves to `resulted`; review act moves to `reconciled`.
- Depends on: SIGN-OFF (§3), INBOUND PIPELINE, TASK.
- Test: `order.lifecycle` drives one order through every state and asserts the state table has exactly one row per transition and that skipping `checked` is rejected.

### INBOUND PIPELINE

- Canon: Spine, "Inbound: receiving, matching and feeding the real-time picture".
- Is: the single intake for results, reports, letters, dispense events, device data, messages and scans.
- Interface: channel adapters (HL7 v2 ORU/ORM, FHIR Bundle, secure messaging, eRx exchange, device gateway, portal, OCR intake) each producing `InboundItem{channel, raw_ref, received_at, sender, format}`.
- Algorithm: (1) store raw artefact immutably (content-addressed); (2) MASTER PATIENT IDENTITY match; (3) order match: for pathology, line match on `(LOINC, specimen, collection time)`; unmatched lines flagged `unsolicited`; (4) write FHIR resources (`DiagnosticReport`, `Observation[]`, `DocumentReference`) with provenance `capture_context = imported`; (5) dispatch to the LANGUAGE ENGINE for extraction (§2) producing GROUNDS and SPAN LINKS; (6) classify and route to a queue by urgency (§8 REVIEW QUEUE); (7) advance ORDER OBJECT state; (8) emit RECORD EVENT. Steps 1–4 are synchronous within 5 s budget; 5–7 are consumers.
- Test: `inbound.pathology_line_match` sends a panel with one extra analyte and asserts the extra is stored as unsolicited and the order shows `resulted` only when all ordered lines are present.

### SPAN LINK

- Canon: Spine, "Clinical documents" ("the link between text span and extracted fact preserved"); moonshot architecture ("every fact carries its source passage").
- Is: the bidirectional link between an extracted fact and the characters it came from.
- Data: `span_link(fact_ref, document_ref, version_id, start_char int, end_char int, text_sha256, extractor_pin)`; stored on the fact as FHIR extension `source-span` and indexed by document.
- Algorithm: offsets are over the canonical UTF-8 text of the stored document version; `text_sha256` guards against re-extraction drift; a fact without a span link is invalid when `capture_context = extracted`.
- Test: `span.roundtrip` extracts, then re-reads the substring by offsets and asserts hash equality.

### RECORD EVENT and EVENT STREAM

- Canon: Spine, "Event stream".
- Is: an immutable message per write, delivered to durable, filtered, replayable subscriptions.
- Data: `Event{event_id ULID, topic, patient_id, resource_type, resource_id, version_id, actor, effective_time, reason, content_hash, prev_event_hash}`; topics: `record.*`, `draft.submitted`, `argument.*`, `act.recorded`, `generic_argument.ratified`, `conflict.recorded`.
- Algorithm: transactional outbox (event row written in the same transaction as the resource); relay publishes to the broker with at-least-once delivery; consumers are idempotent on `event_id`; replay = re-read outbox from an offset. Priority lanes: `critical` (critical results, hard stops) drains before `routine`.
- Depends on: broker with ACLs (§6.5 of the consolidated spec).
- Test: `events.outbox_atomic` kills the process between resource insert and event publish and asserts the event still publishes after restart; `events.priority` asserts a critical result overtakes 1,000 queued routine letters.

### FACT GRAPH

- Canon: moonshot, "Longitudinal fact graph"; Spine, "The AI-native core".
- Is: a per-patient materialised view of entities and typed relations over the record, kept current by events, used by engines as GROUNDS input.
- Data: node `(patient_id, node_id, kind: condition|medication|finding|result|procedure|social|goal, code{system, code}, assertion, onset, end, source_refs[], capture_context)`; edge `(from, to, predicate: treats|indicates|caused|measured|contraindicates|monitors, source_refs[], since)`; `disagreement(node_a, node_b, field, values[])` for unresolved conflicts between sources.
- Algorithm: consumer of `record.*`; upserts nodes keyed by `(patient, kind, code)`; never merges two sources' conflicting values, writes a `disagreement` row instead; serialisable as a FHIR Bundle for replay; held in memory per active patient (LRU) and persisted as rows.
- Test: `graph.disagreement` ingests two documents with different onset dates for one condition and asserts one node and one disagreement row.

### CONSENT

- Canon: Spine, "Consent"; three portals, "Consent, transparency and control".
- Is: a FHIR `Consent` resource per purpose, evaluated on every read for secondary use, every export and every agent contact.
- Data: `Consent{scope, category (care|secondary-use|research|trial-contact|agent-contact), provision{type: permit|deny, period, actor[], purpose[], dataPeriod}}`; withdrawal = new version with `deny`.
- Algorithm: `consent.check(patient, purpose, actor, resource) -> allow|deny` evaluated by the ABAC policy engine (§10); withdrawal event propagates to subscribers which drop pending contacts.
- Test: `consent.withdraw_propagates` withdraws research consent and asserts a queued export job aborts within one poll interval.

## 2. Language engine

The language engine is the capability catalogue of the [moonshot](https://claude.ai/code/artifact/4aa8a883-e0b5-4667-a01b-2f1ce919ebc8) made concrete. Every component is a **class-2 frozen model** in the corpus's sense ([OM-9](https://github.com/Arepo-Medtech/CDSS-makoha-imago-V2.0/blob/bdd26226f0cb1f1d797a8498dec90f12e20e175c/corpus-md/compound-eyes-corpus_v1.4.md#om-9-must)): it produces GROUNDS and drafts, never released content; it carries a declared error rate on a fixed benchmark; its weights hash is pin element W. Development corpus: [syn500](https://github.com/Arepo-Medtech/syn500). Shared pipeline contract:

```
ExtractionRequest  { document_ref, version_id, text (canonical UTF-8), locale_pack: Pin, models: Pin[], effective_time }
ExtractionResult   { document_ref, version_id, mentions[], relations[], facts[], classification, extractor_pins: Pin[], benchmark_ref }
Mention            { id, start_char, end_char, text_sha256, entity_type, candidates[]{system, code, display, score}, assertion, temporality, experiencer, reliability }
Relation           { id, from_mention, to_mention, predicate, score }
Fact               { id, kind, code{system, code}, value?, unit?, onset?, end?, assertion, mention_refs[], relation_refs[], capture_context: extracted }
```

Every stage writes its own `benchmark_ref` (dataset id, snapshot, macro-F1, per-class F1, CI) into the result; the pipeline refuses to run a model whose benchmark is older than its weights.

### CLINICAL ENTITY RECOGNITION

- Canon: moonshot, capability catalogue row 1.
- Is: token-level tagging of clinical mentions into typed spans.
- Interface: `ner(text, locale_pack) -> Mention[]` with `entity_type ∈ {condition, symptom, medication, dose, route, frequency, procedure, test, result, anatomy, device, allergy, social_factor, vital}`.
- Data: BIO-tagged spans over the canonical text; offsets are character offsets, not token offsets.
- Algorithm: transformer token classifier fine-tuned on Australian GP text (syn500 plus licensed corpora under CP-11); locale pack supplies abbreviation and brand lexicons as post-processing rules; output deterministic (greedy decode, fixed seed, batch-invariant kernels).
- Test: `nlp.ner_benchmark` grouped-type F1 ≥ the registered floor on the sealed benchmark; `nlp.ner_determinism` two runs byte-identical.

### ASSERTION STATUS

- Canon: moonshot, capability row 2; [risk-adjustment reading](https://www.johnsnowlabs.com/nlp-risk-adjustment-clinical-notes-evidence-extraction/) (conditional statements are the hard class).
- Is: per-mention classification into `present | absent | possible | hypothetical | conditional | historical` plus `experiencer ∈ {patient, family, other}`.
- Algorithm: span-pair classifier over (mention, sentence window); rule floor first (class 1: negation cues, family-history section headers from the openEHR/section parser), model second (class 2); the two disagreeing sets `assertion_conflict = true` on the mention and the fact is written with `verificationStatus = provisional` and routed to review.
- Test: `nlp.assertion_hard_classes` reports per-class accuracy; `conditional` and `family` classes each above the registered floor; any fact with `experiencer = family` written as a patient Condition is a suite failure.

### RELATION EXTRACTION

- Canon: moonshot, capability row 3.
- Is: typed links between mentions.
- Interface: `relations(mentions, text) -> Relation[]` with `predicate ∈ {has_dose, has_route, has_frequency, has_duration, for_indication, finding_site, has_value, has_unit, treats, caused_by, temporal_after}`.
- Algorithm: pairwise classifier constrained by a predicate register (which entity types may be joined by which predicate, mirroring Graph-Ontology's [graph\_predicates.json](https://github.com/Arepo-Medtech/Graph-Ontology/blob/517d7e666da8e6e126ab76568bd25082b214af94/reference/graph_predicates.json) discipline); unregistered predicate pairs are impossible outputs.
- Test: `nlp.relation_register` asserts every emitted relation's `(from.entity_type, predicate, to.entity_type)` is registered.

### TERMINOLOGY GROUNDING (entity resolution)

- Canon: moonshot, row 4; v1 corpus [grounding\_and\_weak\_supervision.md](https://github.com/Arepo-Medtech/CDSS-makoha-imago/blob/d893e4a42f572ae71084b29f5087a8ad3ef8a986/02_cdss-stack-augmented/grounding_and_weak_supervision.md).
- Is: mapping a mention to concepts in the pinned TERMINOLOGY SNAPSHOT (SNOMED CT-AU for findings/procedures, AMT for medicines, LOINC for tests).
- Interface: `ground(mention, snapshot: Pin) -> candidates[]{system, code, display, score, method}`; `method ∈ {exact_synonym, normalised, lexical_index, encoder_similarity, brand_amt_fs}`.
- Algorithm: (1) exact and normalised synonym match against the snapshot's description index (class 1); (2) lexical index (BM25) over descriptions; (3) frozen bi-encoder similarity (class 2) for the remainder; (4) medicines go through the FELLEGI–SUNTER RESOLVER for brand→AMT with per-field weights; candidates keep their method so the argument can show why; top candidate becomes the fact's code only if `score ≥ template floor`, else the fact is `unbound` and routed to the binding review queue ([docs/binding-review-queue.md](https://github.com/Arepo-Medtech/Graph-Ontology/blob/517d7e666da8e6e126ab76568bd25082b214af94/docs/binding-review-queue.md) pattern).
- Test: `nlp.grounding_top5` top-5 accuracy on the sealed benchmark ≥ floor; `nlp.grounding_snapshot_pinned` asserts no call reaches a live terminology server.

### TEMPORAL EXTRACTION

- Canon: moonshot, row 5.
- Is: onset, duration, sequence and recency per fact, anchored to the document's `effective_time`.
- Data: `Fact.onset`, `Fact.end` as ISO-8601 with precision (`day|month|year|relative`), `temporal_expression_span`, `anchor_rule`.
- Algorithm: TIMEX normalisation (rule-based, class 1) for explicit dates and relative expressions ("3 weeks ago" = document date minus 21 days, precision `day`); model (class 2) only for implicit ordering; every derived date records the rule id.
- Test: `nlp.timex_rules` 200 fixtures with expected normalised dates.

### DOCUMENT CLASSIFICATION and ROUTING

- Canon: moonshot, row 6; Spine, "Routing and triage".
- Is: document type and clinical urgency.
- Interface: `classify(document) -> {type: letter|discharge|pathology|imaging|referral|care_plan|patient_message|other, sections[], urgency: critical|urgent|routine, urgency_grounds[]}`.
- Algorithm: type by classifier plus header rules; sections by the section parser ported from [Defunct\_Makoha/ingestion/structuring/section-parser.js](https://github.com/Arepo-Medtech/Defunct_Makoha) mapped to openEHR archetype sections from [ckm](https://github.com/Arepo-Medtech/ckm); urgency is **not** a free model score: it is a rule set over extracted facts (critical result codes, red-flag symptom list, medication change in a discharge) with the firing rule recorded in `urgency_grounds[]`.
- Test: `nlp.urgency_is_rule_backed` asserts every non-routine urgency has ≥ 1 rule id.

### CLINICAL PHENOTYPING

- Canon: moonshot, row 7; Spine, "Registers from narrative".
- Is: cohort membership computed from facts (narrative and coded) by a versioned phenotype definition.
- Data: `PhenotypeDefinition{id, version, ecl_inclusions[], ecl_exclusions[], observation_predicates[], medication_predicates[], temporal_window, licence_class}` compiled through the COMPILER (§4) like any template.
- Algorithm: deterministic evaluation over the FACT GRAPH with SNOMED subsumption from the pinned snapshot; output `PhenotypeMembership{patient, phenotype: Pin, as_of, grounds[]}`; runs as an event consumer and nightly.
- Test: `pheno.register_equals_manual` on a synthetic practice with known truth: recall and precision ≥ floors; deceased and resolved excluded.

### DE-IDENTIFICATION

- Canon: moonshot, row 14.
- Is: removal or surrogate replacement of direct identifiers across text, FHIR, PDF, DICOM.
- Interface: `deidentify(artefact, policy: Pin) -> {artefact', report{entities_removed[], residual_risk}}`.
- Algorithm: NER for PHI classes (names, dates, addresses, identifiers, contacts) with rule floor (regex for Medicare/IHI formats) and consistent surrogates per patient within an export; date shifting by a per-patient offset; DICOM tag policy from the pinned profile; the export cannot contain a direct-identifier field by type (a `DeidentifiedExport` type has no identifier slots).
- Test: `deid.leak_probe` runs the PHI NER over the output and asserts zero hits above the registered floor; `deid.type_exclusion` compile-time test that identifier types are absent from the export struct.

### SUMMARISATION and RECORD Q&A

- Canon: moonshot, rows 12–13; three portals, "The pre-visit brief".
- Is: generated text over the record, always derived, always cited, never a released clinical claim.
- Interface: `summarise(patient, scope, register, template: Pin U) -> {text, claims[]{span, fact_refs[]}, fidelity_check_ref}`; `ask(patient, question) -> {answer, fact_refs[], passages[]}`.
- Algorithm: retrieval over the FACT GRAPH and SPAN LINKS (no free-text index on the release path; retrieval is by facts); generation by a base model under the BOUNDED GENERATIVE LOOP (§5); every sentence decomposed into atomic claims and passed through the REGISTER-FIDELITY TESTER (§9); output labelled `derived`; a summary with any failed claim is not shown, the deterministic brief is shown instead ([HW-6](https://github.com/Arepo-Medtech/CDSS-makoha-imago-V2.0/blob/bdd26226f0cb1f1d797a8498dec90f12e20e175c/corpus-md/head-corpus_v1.1.md#hw-6-should)).
- Test: `gen.fidelity_gate` seeds a summary with one unsupported sentence and asserts it is withheld.

### AMBIENT CAPTURE

- Canon: moonshot, "During the encounter"; consolidated spec §13 D-10.
- Is: speech-to-text of the consultation producing a transcript document, extracted like any document; it enriches the record and produces drafts, it never renders a claim itself.
- Data: `DocumentReference{type: transcript, content: diarised segments with timestamps}`; consent flag `ambient_consent` on the Encounter required before recording starts.
- Algorithm: streaming ASR (class 2) → transcript segments committed as document versions every N seconds → EXTRACTION per segment → facts with `capture_context = extracted` and `source = transcript`; note drafting at end via SUMMARISATION with `template = note`.
- Test: `ambient.consent_gate` asserts no audio is stored without the consent flag; `ambient.drafts_only` asserts no `argument.released` originates from a transcript event without passing the evaluator.

### PATIENT VOICE and SOCIAL DETERMINANTS

- Canon: moonshot, rows 10–11; three portals, "Agentic pre-intake".
- Is: extraction from the patient's own words (messages, questionnaires, intake) of distress, priorities and social factors.
- Data: facts with `kind = social` coded to SNOMED social context concepts; distress as a `Reliability`-typed signal on the ground (source-stated), never a probability; patient's own phrasing stored verbatim (escape hatch, [TA-3](https://github.com/Arepo-Medtech/CDSS-makoha-imago-V2.0/blob/bdd26226f0cb1f1d797a8498dec90f12e20e175c/corpus-md/thorax-corpus_v1.2.md#ta-3-must)).
- Algorithm: linguistic answers map to codebook terms (§4 CODEBOOK) as Membership annotations; free text is extracted but flagged `patient-reported`; a message's urgency is rule-backed as in DOCUMENT CLASSIFICATION.
- Test: `voice.verbatim_preserved` asserts the original text survives every transformation.

## 3. Argument and signals

### ARGUMENT OBJECT

- Canon: [SPINE-1](https://github.com/Arepo-Medtech/CDSS-makoha-imago-V2.0/blob/bdd26226f0cb1f1d797a8498dec90f12e20e175c/corpus-md/four-faces-corpus_v1.4.md#spine-1-must), [SPINE-2](https://github.com/Arepo-Medtech/CDSS-makoha-imago-V2.0/blob/bdd26226f0cb1f1d797a8498dec90f12e20e175c/corpus-md/four-faces-corpus_v1.4.md#spine-2-must); consolidated spec §3.

- Data: the six TOULMIN ELEMENTS as fields; identity, pins, evaluation, hash-chain fields per the consolidated spec §3.2.
- Algorithm: construction is the only way to obtain a value; every constructor checks the invariants R-01..R-22 of the [ARG-1 spec §3](https://claude.ai/code/artifact/4e5eb57b-f675-4162-ae93-bb7c0a2a694f); `content_hash` computed in the constructor over RFC 8785 bytes excluding itself.

- Test: `arg.schema_parity` (Rust types ↔ generated schema), `arg.invariants` (one fixture per rule).

### SIGNAL COMPONENTS (six)

- Canon: [OM-3](https://github.com/Arepo-Medtech/CDSS-makoha-imago-V2.0/blob/bdd26226f0cb1f1d797a8498dec90f12e20e175c/corpus-md/compound-eyes-corpus_v1.4.md#om-3-must), [QU-6](https://github.com/Arepo-Medtech/CDSS-makoha-imago-V2.0/blob/bdd26226f0cb1f1d797a8498dec90f12e20e175c/corpus-md/compound-eyes-corpus_v1.4.md#qu-6-must), MAK-AMB AM-1.
- Is: six non-coercible newtypes; a Qualifier is a non-empty set of them.

```rust
pub struct Posterior   { hypothesis: Code, probability: Fixed6, model: Pin }
pub struct Coverage    { prediction_set: BTreeSet<Code>, coverage: Fixed6, population: String, calibration: Pin }
pub struct Membership  { subject: Code, degree: Fixed6, linguistic_variable: Pin, term: String }
pub struct Reliability { report_ref: Uri, reported_degree: Fixed6, source_ref: Uri }
pub struct Fit         { element: Pin, status: FitStatus /* In|Out|Unknown */, attributes: Vec<String>, evidence_refs: Vec<Uri> }
pub struct Ignorance   { measure: IgnoranceKind /* CredalWidth|VennAbersWidth|PlBelGap */, value: Fixed6, backing: Pin }
pub struct Fixed6(u32); // 0..=1_000_000; no From<f64>, no Into<f64>, no Add/Mul across types
pub struct Qualifier(NonEmpty<Signal>);
```

- Algorithm: allowed operations only through named functions: `compare_posteriors(a,b)` (same hypothesis and model pin), `contains(coverage, code)`, `minimum_membership(a,b)` (same subject, variable pin, term), `preserve(reliability)`, `inspect_status(fit)`, `exceeds(ignorance, threshold: Fixed6)`. Any other combination does not compile.
- Test: `signals.non_coercion` (C06 semantics ported to Rust; attempts to add, multiply, cast or mix types are compile-fail tests via `trybuild`).

### IGNORANCE

- Canon: MAK-AMB Part 3 item 2 and AM-1 ([ambiguity-mathematics\_v1.1.md](https://github.com/Arepo-Medtech/CDSS-makoha-imago-V2.0/blob/bdd26226f0cb1f1d797a8498dec90f12e20e175c/corpus-md/ambiguity-mathematics_v1.1.md)); QU-6.
- Is: how little evidence there is, separate from how the evidence is spread.
- Algorithm (three ratified routes, one chosen per template): (a) **credal width** from the Imprecise Dirichlet Model on DX-3 parameters: for a parameter with counts `n_i` and prior strength `s`, lower `n_i/(N+s)`, upper `(n_i+s)/(N+s)`; width propagates through the differential by interval arithmetic and the posterior width is the ignorance value; (b) **Venn–Abers width** `p1 - p0` from the calibration wrapper; (c) **Pl−Bel gap** from an evidential representation when a template declares mass functions. The value is `Fixed6` in \[0,1\]. It is never subtracted from, added to, or rendered beside a posterior as confidence.
- Routing: `exceeds(ignorance, template.max_ignorance)` ⇒ stage-2 outcome `defer` ⇒ the request-more-data branch (INFORMATION-GAIN ORDERING, §5), not a low-confidence rendering.
- Test: `ignorance.uniform_vs_empty` two fixtures with identical posterior spread (uniform over 3) but N=300 vs N=0 evidence yield ignorance near 0 and near 1 respectively.

### LOSS MATRIX

- Canon: MAK-AMB AM-3 → [RG-9](https://github.com/Arepo-Medtech/CDSS-makoha-imago-V2.0/blob/bdd26226f0cb1f1d797a8498dec90f12e20e175c/corpus-md/compound-eyes-corpus_v1.4.md#rg-9-must).
- Is: the ratified costs from which the gate's release/defer/hold boundaries are derived.
- Data: `LossMatrix{version, ratified, lambda: {PP, PN, BP, BN, NP, NN}: decimal}` per template, where the first letter is the action (P release, B defer, N hold) and the second the true state (P claim supported, N not).
- Algorithm (Yao's three-way rule): `alpha = (λ_PN − λ_BN) / ((λ_PN − λ_BN) + (λ_BP − λ_PP))`, `beta = (λ_BN − λ_NN) / ((λ_BN − λ_NN) + (λ_NP − λ_BP))`, computed once at template load in fixed-point; stage 5 compares the evidence-supported probability `p` (Posterior where present; else the deterministic criterion outcome mapped to 1, 0, or the borderline midpoint) against them: `p ≥ alpha` ⇒ release, `p ≤ beta` ⇒ hold, between ⇒ defer (flagged). Fellegi–Sunter fixed-error thresholds are the special case where λ is chosen from target error rates.
- Test: `loss.alpha_beta_derivation` against hand-computed values; `loss.only_matrix_moves_boundary`.

## 11. Additive services that flow from the build

Three services fall out of the components above without new architecture. Each is specified as a service the spine hosts: what it reads, what it computes, what it exposes, and which existing terms it is built from. They are additive to the canon and obey the same laws (no engine path to a face; every fact sourced; every output pinned).

### 11.1 PATIENT JOURNEY SERVICE

- Is: the longitudinal, event-ordered view of one patient across every source, and the cohort and pathway queries over many patients, computed from the FACT GRAPH and the ledger rather than from a separate warehouse.
- Built from: RECORD EVENT (ordering), FACT GRAPH (nodes and relations), SPAN LINK (provenance to text), MEDICATION LIFECYCLE and ORDER OBJECT (state transitions as journey events), CLINICAL PHENOTYPING (cohort definitions), CONSENT (secondary-use gating), DE-IDENTIFICATION (population views), TERMINOLOGY SNAPSHOT (subsumption in queries).
- Data model:

```
JourneyEvent { patient_id, event_id, at: EffectiveTime, precision, kind: diagnosis|medication_start|medication_change|medication_stop|procedure|result|encounter|order_state|admission|discharge|device_event|patient_report|argument_released|act,
               code{system, code}, value?, source_refs[], capture_context, assertion, episode_ref?, arg_ref? }
Journey      { patient_id, events[] ordered by (at, kind_rank, event_id), episodes[] {episode_ref, start, end, kind}, disagreements[] }
CohortQuery  { phenotype: Pin | inline definition, index_event, window{before, after}, inclusion[], exclusion[], outcome_events[], as_of }
Pathway      { cohort_ref, sequence_pattern: [event_kind|code sets], gaps_allowed, min_support }
```

- Interface:
  - `GET /journey/{patient_id}?from&to&kinds` → `Journey` (role-authorised; patient role sees own journey in the plain register with content classes typed).
  - `POST /cohort/query {CohortQuery}` → `{cohort_id, size, members[] (de-identified unless authorised), grounds_per_member[]}`; runs as a deterministic evaluation over the FACT GRAPH; every membership carries the grounds that satisfied the definition.
  - `POST /pathway/mine {cohort_id, Pathway}` → frequent sequences with support and typical intervals (prefix-span over ordered event kinds; deterministic; results carry the member lists).
  - `POST /journey/measure {cohort_id, measure: Pin}` → computed clinical measures (eGFR CKD-EPI, BMI, HbA1c control bands, PIP-QI style indicators) as Observations with `derivedFrom[]` and calculator pins.
  - `GET /journey/{patient_id}/timeline.svg|json` for the auditor and clinician faces (rendered from `Journey`, element-mapped like any register).
- Algorithm: (1) journey materialisation is an event consumer: every `record.*`, `argument.released`, `act.recorded` and order-state event appends a `JourneyEvent`; (2) ordering key is `(at, kind_rank, event_id)` with `precision` retained so a year-precision onset never sorts as a day; (3) disagreements between sources are kept as `disagreements[]` and rendered as such (no automatic reconciliation on the release path; a reconciled view is a derived projection labelled as derived); (4) cohort evaluation compiles the `CohortQuery` to a plan over the graph with ECL expansion from the pinned snapshot, then evaluates per patient deterministically; (5) natural-language cohort questions are accepted only through the BOUNDED GENERATIVE LOOP producing a `CohortQuery` draft that a human confirms before execution (the query text is stored with the draft's pins); (6) population outputs pass through DE-IDENTIFICATION and CONSENT checks per purpose.
- Storage: `journey_event` table partitioned by `patient_id`; columnar mirror for cohort scans (rebuildable from events); OMOP CDM export as a projection (`person`, `condition_occurrence`, `drug_exposure`, `measurement`, `visit_occurrence`) using the Graph-Ontology AMT→OMOP and SNOMED→OMOP bridges ([docs/au-snomed-to-omop.md](https://github.com/Arepo-Medtech/Graph-Ontology/blob/517d7e666da8e6e126ab76568bd25082b214af94/docs/au-snomed-to-omop.md)), for external analysts who want SQL against a standard model.
- What it enables: the pre-visit brief's trend lines; sentinel-event timelines (three portals, "Sentinel events and incident learning"); care-gap identification as a cohort query against guideline templates; trial matching as a cohort query against eligibility criteria compiled as templates; prospective studies (three portals, "Configuring prospective studies") as a `CohortQuery` with an enrolment subscription on `journey_event`.
- Tests: `journey.order_precision`; `journey.disagreement_preserved`; `cohort.grounds_per_member`; `cohort.consent_gate`; `omop.export_roundtrip`.

### 11.2 TERMINOLOGY SERVICE

- Is: the TERMINOLOGY SNAPSHOT served as a network service with FHIR terminology operations, text-to-code search, cross-system mapping, custom value sets and agent tools, all answering from pinned editions.
- Built from: TERMINOLOGY SNAPSHOT (editions, AMT compendium, LOINC, ICD-10-AM), PREDICATE REGISTER and TIER (which maps are trusted at which tier), TERMINOLOGY GROUNDING (text-to-code), FELLEGI–SUNTER RESOLVER (brand→AMT), PIN REGISTRY (edition pins).
- Code systems served (from the Graph-Ontology build): SNOMED CT-AU (all built editions), AMT (TPUU/TPP/CTPP/MPUU/MPP/MP/brand), LOINC, ICD-10-AM/ICD-10-CM/ICD-10-WHO maps, ATC, PBS item and restriction codes, MBS, RxNorm (via bridges), OMOP standard concepts, HPO, MONDO, UBERON, RadLex; each with edition identifier and licence class.
- Interface (FHIR R4 terminology operations over the pinned snapshot, plus extensions):

| Operation | Behaviour |
| --- | --- |
| `GET /fhir/CodeSystem/$lookup?system&code&version` | FSN, preferred term, synonyms, properties, edition pin |
| `POST /fhir/ValueSet/$expand` with ECL or a stored ValueSet | expansion from precomputed closures; `expansion.parameter[edition]` carries the pin; count and offset paging |
| `GET /fhir/CodeSystem/$subsumes?codeA&codeB&system` | \`subsumes |
| `POST /fhir/ValueSet/$validate-code` | membership at the pinned edition, with `inactive` reported |
| `POST /fhir/ConceptMap/$translate` | source→target using Graph-Ontology maps; every match carries `tier`, `method` and `source`; Tier-3 maps are returned only when `include_tier3=true` and are labelled |
| `GET /terminology/search?text&system&domain&edition` | text-to-code: exact and normalised synonym, lexical index, then frozen-encoder ranking; results carry `method` and never a bare confidence (score typed as retrieval rank) |
| \`POST /terminology/resolve-medication {text | brand |
| \`POST /terminology/valueset {csv | ecl, name, version}\` |
| `GET /terminology/editions` | the pinned editions available and their sha256 |
| Agent tools (MCP-style): `terminology.lookup`, `terminology.expand`, `terminology.translate`, `terminology.search` | same permissions as the REST surface; every answer carries the edition pin so an agent's draft can pin element S |

- Algorithm: read-only; loads a snapshot by pin at startup and serves from memory-mapped closure tables; `$translate` walks the graph via registered predicates only (`omop:maps_to`, `sct:icd10_map`, `std_ingredient`, `in_atc_class`, `corpus:binds_to`, ...) with a visited set and depth cap, skipping `state=rejected`; search uses the same three-stage grounding as the language engine so codes chosen by a human and by extraction agree; every response includes `X-Terminology-Edition: <pin>`.
- Versioning: a new edition is a new snapshot pin; the service can host several concurrently (one per deployment profile or study) and never mutates a served snapshot; the Graph-Ontology `snomed_editions.py check` replay is the acceptance test for a new edition.
- What it enables: coding at write time in the RECORD; envelope ECL evaluation in the EVALUATOR at the same edition the template was compiled against; prescribing checks over reconciled AMT products; external systems (labs, pharmacies, other EHRs) validating codes against the same pins; the patient face's codebook lookups.
- Tests: `terminology.fhir_ops_conformance` (HL7 terminology test cases); `terminology.translate_tier_labelled`; `terminology.replay_expansions`.

### 11.3 EVIDENCE-LINKED CODING and RISK-REGISTER SERVICE

- Is: continuous extraction of conditions and risk-relevant facts from narrative with span-level evidence, assertion and temporality resolution, code assignment to SNOMED CT-AU and ICD-10-AM (and, where a jurisdiction needs it, ICD-10-CM and condition-category groupers), suspect and gap surfacing, a coder review workflow, and a complete audit chain per code. In the Australian primary-care setting its products are complete problem lists, chronic-disease registers, care-plan and MBS-item eligibility, PIP-QI indicators and funding-accurate claims; the same pipeline supports risk-adjustment groupers where a payer requires them.
- Built from: INBOUND PIPELINE and AMBIENT CAPTURE (sources), CLINICAL ENTITY RECOGNITION, ASSERTION STATUS, TEMPORAL EXTRACTION, TERMINOLOGY GROUNDING (facts with span links), CLINICAL PHENOTYPING (register membership), TERMINOLOGY SERVICE (`$translate` SNOMED→ICD-10-AM at a pinned map tier), REVIEW QUEUE (coder review), ARGUMENT OBJECT and EVALUATOR (a proposed code is a claim of type `coding-proposal` released through the gate, so every code has grounds, warrant, backing, qualifier and rebuttals), LEDGER (audit chain), CLASS-2 TESTER (entailment of the code by its evidence span).
- Data model:

```
CodingProposal (an ActualArgument with claim.type = coding-proposal)
  claim.content      = { target_system: SNOMED-CT-AU | ICD-10-AM | ICD-10-CM | grouper, code, display, weight_class?: low|high }
  grounds[]          = facts with span_link, assertion (must be present, experiencer = patient), temporality (active unless the code family admits historical), capture_context
  warrant            = template: coding rule for that code family (e.g. "type 2 diabetes with nephropathy requires an active diabetes fact and a renal complication fact within window W")
  backing[]          = the coding standard clause (ACS for ICD-10-AM; SNOMED editorial guide) as pinned citations
  qualifier          = Reliability (source-stated), Fit (envelope: document type, specialty), Ignorance where the model's assertion class is conditional
  rebuttals[]        = contradicting facts (a later "resolved", a family-history mention of the same concept), adversary findings on the coding template
  evaluation.verdict = released (auto-accept for low-weight codes) | flagged (high-weight or conditional-assertion codes go to coder review) | held
CodeDecision (act, kind = review) { proposal_arg_id, coder_id, decision: accept|reject|amend{code}, reason_code, at }
Suspect { patient_id, condition_code, evidence_refs[], reason: documented-not-coded | lab-pattern | medication-implies | prior-year-not-recaptured, status }
```

- Pipeline: (1) on every `record.*` document or transcript event, extraction produces facts with spans; (2) the coding ommatidia (one per code family, compiled from coding-rule templates) propose `CodingProposal` drafts from facts; (3) the EVALUATOR runs the five stages; the LOSS MATRIX for coding templates weights false-positive high-weight codes heavily, so high-weight proposals land in `flagged` and route to the coder REVIEW QUEUE, low-weight proposals with `present`/`patient`/`active` assertion release automatically; conditional or family assertions never release (rule floor at stage 1: C-07 plus a coding-specific check that `experiencer = patient`); (4) released and accepted proposals write `Condition` (SNOMED) with `verificationStatus = confirmed` and the ICD-10-AM map via `$translate` at the pinned tier, plus `Claim`-side codes for billing; (5) suspects are produced by phenotype queries (documented-but-uncoded, lab or medication patterns implying a condition, prior-period codes not recaptured) and rendered as gather-more-information claims to the clinician, never as auto-codes; (6) every code carries the audit chain: source document version, span, extractor pins, coding template pin, evaluator version and trace, reviewer decision, all in the ledger; (7) register and indicator computation runs as CLINICAL PHENOTYPING over confirmed Conditions and Observations.
- Interface: `GET /coding/proposals?patient&state`; `POST /act/review {proposal_arg_id, decision}`; `GET /coding/suspects?practice&condition`; `GET /coding/audit/{code_instance}` → full chain; `GET /registers/{phenotype}` and `GET /indicators/{set}` (PIP-QI style) with lineage per numerator and denominator member; `GET /claims/preview?encounter` (codes and MBS items with evidence).
- Guarantees: a code without an evidence span is unrepresentable (type-level); a code whose evidence has `experiencer ≠ patient` or `assertion ∉ {present}` cannot release; high-weight codes require a human `review` act; the audit endpoint reproduces the chain from the ledger alone (the same reconstruction property as the REGULATOR BUNDLE).
- Metrics (auditor lens): coder acceptance rate by code family, assertion-class error rates against the sealed benchmark (conditional and family classes reported separately), suspect conversion rate, register completeness against manual audit, time from document arrival to confirmed code.
- Tests: `coding.no_family_history_release`; `coding.high_weight_requires_review`; `coding.audit_chain_reconstructs`; `coding.suspect_never_autocodes`; `registers.completeness_vs_manual`.
